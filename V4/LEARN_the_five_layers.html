One prompt, then five more layers around it

A language model is a fixed function. It has no memory, no access to your files, and no way to check its own work. Everything you actually want from it lives in the text you put around it — and in the code that decides what that text should be.

Start with a single instruction. Add one layer at a time and watch the prompt on the right grow. By the last layer, the machine is writing that text itself.

Layers

LAYER 0

What you are actually talking to

Before any of the engineering makes sense, three words have to mean something precise: token, weights, context window.

Tokens — the units the model actually sees

A model does not read words. Text is chopped into tokens: common words are usually one token, rarer and longer words split into pieces, and every space and punctuation mark costs something. Roughly ¾ of a word each in English, and noticeably worse for languages the tokenizer saw less of during training — which is a real equity issue for a UNESCO audience, because the same sentence in Amharic or Khmer can cost several times more than in English.

Type anything — watch it become tokensapproximate

This splitter is a rough imitation for teaching, not a real tokenizer. Real ones are learned from data. The lesson it gets right is the one that matters: your text becomes a countable number of pieces, and you are billed — in time, memory and quality — per piece.

Weights — fixed at training, never updated by you

The weights are billions of numbers, frozen the day training finished. Four things follow, and almost every misunderstanding in this field is a failure to accept one of them:

  • No memory. Every call starts from nothing. Anything it "remembers" was put back in by software.
  • No access. It cannot see your files, your email or the web unless something fetched them and pasted them in.
  • No looking up. It produces what fits the patterns it learned. When those patterns and the truth coincide, the output is right. It cannot tell the two cases apart.
  • No doing. It emits text. If a file got written, other code wrote it.
The consequence worth memorising

"We trained the AI on our documents" is almost always false. The documents sit in a folder, and passages are copied into the prompt at question time. That is good news: you can update it in seconds, and you can delete from it.

Context window — one budget, everything competes

Each call accepts a maximum number of tokens. Instructions, retrieved documents, the conversation so far, and the answer all come out of the same allowance. "Just give it all our documents" fails for an unglamorous reason: they do not fit. And where they do fit, quality falls as the relevant sentence gets buried.

So something has to choose what goes in. Everything from layer 1 onwards is a progressively better answer to that one question.

What it fixes, and where it stops

Prompting fixes ambiguity: the model answered the wrong question and you asked a better one. It stops at the point where you are typing the same conventions for the fourth time this week, and getting slightly different results each time because you phrased them slightly differently.

The honest test for whether you need layer 2

Are you pasting the same paragraph of house rules into the chat window repeatedly? If yes, that paragraph belongs in a file, not in your fingers.

Automating it — 15 lines against a local model

one_call.py — standard library only, no packages to install

import json, urllib.request

# The ONLY network endpoint anywhere in this package. Nothing leaves the machine.
URL = "http://127.0.0.1:11434/api/generate"

def ask(model, prompt):
    body = json.dumps({"model": model, "prompt": prompt,
                       "stream": False}).encode()
    req = urllib.request.Request(URL, data=body,
                                 headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=180) as r:
        return json.loads(r.read())["response"].strip()

print(ask("llama3.1:8b", "Write one learning objective on hydraulic safety."))

That is a complete, working local AI integration. Everything in the remaining layers is code around this function — and in the shipped example, this function stays fifteen lines while the code around it grows to several hundred.

LAYER 2 · SKILL ENGINEERING

Write the conventions down once

You edit a file, not a sentence. The model loads it when the task calls for it, so everyone in the department gets the same conventions on a Friday as on a Monday.

A skill is a folder with a SKILL.md in it: metadata at the top so the system knows when to load it, then the procedural knowledge. Note what has just appeared in the prompt inspector — a second block, above your task. Your task did not change.

This package's own skill files

The teaching package ships five of them, one per role. They are surface-neutral prose in bmad/agents/, with thin adapters that make them appear as agents in VS Code. Here is the shape:

bmad/agents/author.md — excerpt

# @author — teaching material

**Owns:** all prose in the package.

## May write to
Markdown and HTML under part1..part4. NOT the Python.

## House rules
- UNESCO progression levels are Acquire / Deepen / Create (teachers)
  and Understand / Apply / Create (students).
  "AI-literate" and "AI-enhanced educator" are NOT UNESCO's words.
- LiaScript: single choice [( )] / [(X)], multiple [[ ]] / [[X]].
- Re-open sources before asserting anything. Do not paraphrase
  from memory.
- If a claim cannot be verified, SAY SO in the text.
Why that fourth rule is the valuable one

"If a claim cannot be verified, say so" is a convention that would otherwise live in one person's head and be applied inconsistently. Written into a skill file, it applies on every run, to every author, including the machine.

Progressive disclosure — the trick that makes it scale

Skills are not all loaded at once. Each has a short description in its frontmatter; the system reads only the descriptions, and loads the full file only when a task matches. Twenty skill files cost you twenty one-line descriptions of context, not twenty full documents. That is what keeps the context budget from collapsing as your library grows.

Automating it — loading a skill on demand

with_skill.py — the prompt is now assembled, not typed

from pathlib import Path

def load_skill(name):
    # The skill lives on disk, versioned, reviewable, shared by the team.
    return Path(f"skills/{name}/SKILL.md").read_text()

def build_prompt(task, skill_name=None):
    parts = []
    if skill_name:
        parts.append(f"Follow this guidance exactly:\n---\n{load_skill(skill_name)}\n---")
    parts.append(f"Task: {task}")
    return "\n\n".join(parts)          # <- assembly begins here

print(ask("llama3.1:8b", build_prompt("hydraulic safety", "objectives")))

build_prompt() is the first line of harness code on this page. From here on, the prompt is constructed rather than written, and every later layer adds another block to that function.

LAYER 3 · HARNESS ENGINEERING

Memory, tools, and a way to check the work

A harness is everything outside the model weights. Five subsystems: instructions, tools, environment, state, feedback. Three of them just appeared in your prompt.

Simplicity statement

A harness does not make the model smarter. It gives a fixed model a place to keep state, a way to check its own work, and rules for when to stop. Everything else in this package is one worked example of that idea.

The subsystem that pays for itself first

Feedback. Not a nicer prompt — a command that returns pass or fail and cannot be argued with. Until you have one, "done" means "the model stopped talking".

This package's own check is a script with nine tests. It is the arbiter of whether any work in the repository counts as finished:

make verify — the real definition of donereplay of an actual run
Not run.

State — the file that survives you closing the laptop

The model forgets between calls. The repository does not. Two files carry everything: feature_list.json holds the work with a status field, and PROGRESS.md holds what happened and what to do next. One rule prevents most sprawl: exactly one item may be in_progress at a time.

Tools — the list of things that can go wrong

The model never executes anything. It emits text naming an action; your code parses it, decides whether to allow it, runs it, and pastes the result back. "The agent can send email" always means "we wrote code that sends email when the model asks". The permission is yours to withhold.

In this package, the QA agent is defined with no edit tool at all:

.github/agents/qa.agent.md — read-only by design

---
name: QA
description: Verification only. Runs the checks, reports verbatim,
             never fixes what it finds.
tools: ['search/codebase', 'runCommands']   # <- no 'edit'
handoffs:
  - label: Fix teaching content
    agent: Author
---
You are READ-ONLY. You must not ask for an edit tool.

This is the subject of the package, not caution. The reliability
rule taught here is generator/evaluator separation. A QA agent that
fixes what it finds HAS BECOME the generator, and its verdict stops
carrying information.
Generator ≠ evaluator

The agent that produced the work must not be the agent that judges it. A model looking back at its own output sees its reasoning, not its mistakes. Use a command with an exit code, or a different model with different instructions — never the same one twice.

LAYER 4 · LOOP ENGINEERING

The system prompts itself now

You stop supplying the next instruction and start supplying a goal, a verification method, and a stop condition. Those three things are the whole of it.

Run the agent below. It is a faithful replay of this package's agent.py against three input documents. Watch what the harness does when the model proposes something it is not allowed to do.

agent.py — the model proposes, the harness disposesreplay of an actual run
Not started. The stop condition is: every input PDF has a section in the report.

Three gates every proposal passes through

  • Is it a known tool? Five are permitted. Anything else is overridden.
  • Is its precondition met? You cannot summarise a document that has not been converted yet.
  • Did it actually produce a file? Exists and is non-empty, or the step is not marked done and the bookkeeping is rolled back.

Every override is written to agent_log.md in plain sentences, which is why that file is the best five minutes of a workshop: a non-programmer can read exactly where the machine was wrong and where the code caught it.

The stop condition is not optional

A system that chooses and acts but has no written stop condition is not an agent. It is an unbounded expense with write access. This one stops when every input document has a section in the report, with a hard cap of 40 steps as a second line of defence.

The four costs nobody puts in the proposal

CostWhat it looks like
Verification debt"Looks fine" quietly replaces "confirmed correct".
Comprehension rotOutput arrives faster than anyone reads it.
Cognitive surrenderThe loop is used to avoid thinking rather than to amplify it.
Token blowoutContext grows every iteration unless actively managed.

Two people can build the same loop and get opposite results: one goes faster on work they understand, the other avoids understanding the work. The loop cannot tell the difference — which is precisely why items two and three matter so much in an education setting.

Automating it — the loop in twenty lines

loop.py — the retry carries the reason, which is the whole point

MAX_ATTEMPTS = 3                     # bounded. never `while True`.

def solve(task, model):
    complaint = None
    for attempt in range(1, MAX_ATTEMPTS + 1):
        answer = ask(model, build_prompt(task, complaint))
        ok, reason = verify(answer)          # plain code. no model.
        log(f"attempt {attempt}: {reason}")
        if ok:
            return answer
        complaint = reason                   # <- feed the reason back in
    log("gave up; the retry limit IS the stop condition")
    return None

The line that matters is complaint = reason. A retry loop that just asks again is a slot machine. A retry loop that tells the model precisely which rule it broke is engineering.

LAYER 5 · SELF-IMPROVING AGENTS

The loop writes the skill file

Layers 1–4 are things a person writes. At layer 5 the system writes its own layer 2 — and keeps a wiki of everything it learned trying.

This follows WikiSkill (Tang, Rashtchian, Ferng, Tomkins, Juan & Vu, Google Research, August 2026), which builds on Karpathy's proposal for an LLM wiki. The idea is one asymmetry, and everything else follows from it.

The asymmetry that makes it work

A rejected skill is thrown away. What was learned by trying it is not. Skills are gated and rolled back; the wiki only ever grows. That is why the skill stays short while the knowledge compounds.

Three folders, four roles

FolderHoldsLifecycle
raw/Execution traces, completeImmutable. Never edited.
wiki/Patterns, evolution log, audit trailGrows only. Never rolled back.
skills/The active SKILL.mdGated. Reverted if it makes things worse.

Each iteration runs four roles: an Inference Agent does the task with the current skill; a Wiki Maintainer reads the traces and writes patterns; a Skill Proposer reads the wiki and proposes one edit; a Gate scores it on held-out tasks and keeps or reverts it.

wiki_agent.py — watch the skill get writtenreplay of an actual run
Not started. Nobody has written a skill file. Validation score with no skill at all: 0%.
Notice what the Inference Agent is not given

The wiki. Deliberately. The paper's ablation found that letting the working agent read the wiki made the final skill worse — 63.7% down to 60.9% average — because the agent solves the task from the wiki instead of from the skill, and the traces stop revealing what the skill needs to fix. The wiki informs the Proposer, never the worker.

What the published results actually say

FindingNumbers
Skills beat no skillsGemini-3.5-Flash averaged 49.5% → 68.1% across five benchmarks; Qwen-3.6-27B 39.4% → 63.3%.
Skills can substitute for sizeQwen-3.5-9B with evolved skills (47.4%) beat Qwen-3.6-27B without them (39.4%). A smaller model, better organised, won.
The wiki is the active ingredientRemoving persistent knowledge dropped the average from 63.7% to 48.7%. The loop alone is not enough.
Skills transfer between modelsSometimes a model does better with a skill another model evolved than with its own — discovering procedures and executing them are different abilities.
Transfer can also backfireSkills from a 4B model cut Gemini-3.5-Flash from 50.5% to 18.1% on spreadsheets: the small model's low-level workarounds constrained the larger one.

The wiki grows, in Markdown you can read

workspace/wiki/patterns/opened-with-x-not-an-approved-action-verb.md

# Pattern: opened with 'X', not an approved action verb

**First seen:** iteration 1

**What happens:** the answer is rejected because it opens with a noun.

**Example:** `Understanding of hydraulic system safety is something the...`

**Proposed rule:** Begin every objective with an approved action verb
such as identify or inspect.

## Evidence
- Iteration 1: 4 occurrence(s).
- Iteration 2: recurred 3 time(s). Still unresolved.

workspace/wiki/skill-impact.md — the audit trail that stops it repeating itself

## Iteration 3 — ROLLED BACK

- Validation score: 0% (previous best 67%)
- Skill length: 6 lines
- Outcome: reverted; do not propose this again

That last line is what makes the loop converge instead of oscillating. The Proposer reads the impact log before proposing, so a change that has already been rejected is not offered twice.

Read the file before you trust it

At this layer the instructions the model follows were written by a machine and accepted by a score. The score is only as good as the scoring function a person wrote. Check the scorer first, then read the skill — it is short, in Markdown, and takes two minutes.
