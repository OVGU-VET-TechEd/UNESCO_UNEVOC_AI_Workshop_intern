Simplicity Statement — Harness Engineering A harness does not make the model smarter. It gives a fixed model a place to keep state, a way to check its own work, and rules for when to stop. Everything else in this package is one worked example of that idea.

The five subsystems — miss one and the harness is incomplete

InstructionsAGENTS.md — a map, ~100 lines
Toolswhat the agent may do
Environmentone command sets it up
Statememory that outlives a session
Feedbackcheapest to add, biggest return

If it is not model weights, it is harness. The generator must never be the evaluator.

Templates — copy into your repo root

AGENTS.md — the operating rules

# AGENTS.md

## Project
One paragraph: what this repo produces, for whom.

## Stack
- Runtime: python 3.11
- Model:   gemma3:12b @ 127.0.0.1:11434
- Export:  liaex --format scorm1.2

## Start here, every session
1. Read PROGRESS.md
2. Read feature_list.json, take the highest
   priority not_started item
3. Set exactly ONE item to in_progress

## Hard constraints
- No network except 127.0.0.1:11434
- Do not edit outside ./content and ./build
- No "passing" without pasted evidence

## Verification commands
- Structure: python tools/check_module.py FILE
- Export:    liaex --format scorm1.2 FILE
- Full:      make verify   # non-zero on failure

## Definition of done
make verify exits 0 AND evidence is recorded.

## End of session
Update PROGRESS.md: done / in progress /
blocked / next best action.

PROGRESS.md — state that outlives the session

## Current verified state
- Repo root:      ~/microcredential-factory
- Start command:  ./init.sh
- Verify command: make verify
- Next item:      mod-hydraulics-01
- Blocker:        none

## Session record — 2026-07-27
- Goal:         draft mod-hydraulics-01
- Completed:    slides 1-4
- Verify run:   make verify -> FAILED
- Evidence:     logs/verify-2026-07-27.txt
- Next action:  add quiz block, re-run verify

feature_list.json — the work, machine-readable

{
  "features": [
    {
      "id": "mod-hydraulics-01",
      "priority": 1,
      "area": "content",
      "title": "Hydraulic safety - intro module",
      "user_visible_behavior":
        "6 slides, 1 quiz, exports to SCORM 1.2.",
      "status": "not_started",
      "verification": [
        "make verify content/mod-hydraulics-01.md",
        "open SCORM package, confirm quiz scores"
      ],
      "evidence": "",
      "notes": ""
    }
  ]
}

Status: not_started → in_progress → passing, or blocked. Only one item may be in_progress at a time — this single rule prevents most scope sprawl.

The loop, in three parts — level 4

GOAL          what the end state looks like
VERIFICATION  a command with an exit code, or a
              DIFFERENT model with different
              instructions doing the judging
STOP          a written, machine-checkable rule
              (never "when it feels done")

Harness health checklist — run this before trusting anything unattended

  • State persists. Kill the process mid-run and restart — does it know what was already done?
  • Verification exists. Is there a pass/fail command independent of the model’s own opinion?
  • Stop condition defined. Is “finished” written down, not felt?
  • Logs observable. Could a colleague reconstruct what happened, and why, from files alone?
  • Instructions on disk. Are the conventions in the repo, not in someone’s head?
  • Environment reproducible. Does one command set up the machine from scratch?
  • Generator ≠ evaluator. Is the judge different from the maker?
  • Scope bounded. One item in progress; retries capped at N.

Four or fewer boxes ticked: do not run it unattended.
